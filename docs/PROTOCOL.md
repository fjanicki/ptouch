# Brother P-touch raster protocol — implementation specification

Status: research synthesis, 2026-10-08. Primary target: **PT-P710BT**. Companion data file: [`models.toml`](models.toml).

This document is normative for the `ptouch` crate. "MUST/SHOULD/MAY" are used in the RFC 2119 sense. Values that no source confirms are marked **UNKNOWN**. Values that sources give but that have not been checked on hardware are marked **UNVERIFIED**. A conflict between sources is stated where it occurs, followed by the resolution this spec adopts ("**Resolution:**").

## 0. Conventions and source keys

- Hex bytes are written `1B 69 53`. `00×100` means 100 zero bytes. `<w>` is the tape width in mm (one byte). `<n32>` is a 32-bit little-endian integer. `<m16>` is a 16-bit little-endian integer.
- "Pin" means a print-head element across the tape (one dot of the head line). "Line" means one raster line: a full head line in the feed direction.
- Status offsets are 0-based: `st[4]` is the fifth byte of the 32-byte status reply.

## 1. Overview

Brother P-touch tape printers use the same command set on every transport. Byte streams are identical over USB bulk, Bluetooth SPP (RFCOMM), and TCP port 9100 [D1–D4 §1; labellab confirms identical status frames over BT and USB]. The host:

1. Sends an *invalidate* run of `00` bytes, then *initialize* (`ESC @`).
2. Switches the printer to raster mode (`ESC i a 01`).
3. Reads a 32-byte status (`ESC i S`) to learn the model, the loaded tape and any errors.
4. Per page: sends control commands (print information, cut/mode flags, margin, compression), then one raster line per dot in the feed direction (`G` lines, PackBits-compressed or raw), then a print command (`0C` = next page follows, `1A` = last page).
5. Reads 32-byte status frames that the printer pushes during and after printing.

There is no framing, checksum or acknowledgement at the protocol level except the 32-byte status frames. On error the printer discards all buffered data [D2 §5, D4 §6].

Command dialects. The community describes two "dialects" (classic vs "D460BT magic"). This spec treats them as one protocol parameterised per model ([models.toml](models.toml)). The relevant parameters are:

- **`page_command`**:
  - `start_end`: `ESC i z` n9 is 0 on the first page and 1 on later pages.
  - `start_next_end`: n9 is 0 on the first page, 1 on middle pages, and 2 on the last page; a single-page job uses 2. [SDK, D2 §2.3, D4]
- **`protocol_version`**: gates `ESC i p`, `ESC i L`/`ESC i C`, and `ESC i 18` cancel (§3.3).
- **`null_bytes`**: the invalidate length (100, 200 or 300).
- **`head_pins`**: 64, 128 or 560, which sets `bytes_per_line` (8, 16 or 70).
- **Compression default** and **status-notification support**.

The "D460BT magic" `1B 69 64 01 00 4D 00` used by [ptouch-print] is simply `ESC i d` (margin = 1 dot) followed by `M 00` (no compression) [teip, ptouch-print source comment].

## 2. Transports

### 2.1 Bluetooth Classic (SPP over RFCOMM): common rules

Applies to every Bluetooth P-touch model except PT-N25BT, which is BLE-only (§2.7) [AndroidSDK, MacSDK spec DB, D-series SDK support table].

- **Profile:** Serial Port Profile, UUID16 `0x1101` (`00001101-0000-1000-8000-00805F9B34FB`) [MacSDK, AndroidSDK, all community BT implementations].
- **RFCOMM channel:** it MUST be read from the device's SDP record for UUID `0x1101`. It is not a fixed value [MacSDK `getSPPServiceRecord:` + `getRFCOMMChannelID:`; AndroidSDK `createRfcommSocketToServiceRecord`].
  - Observed: PT-P710BT SPP on channel 1, Apple iAP2 on channel 2 [HW]; PT-P300BT channel 1 [labelpi, Ircama]; PT-E560BT and PT-D610BT SPP on channel 2, iAP on channel 1 [zakx, nbuchwitz#18].
  - Every platform SHOULD resolve the channel from SDP (macOS §2.2 step 4; Linux §2.3; Windows does it itself with port 0, §2.4).
  - Fallback when SDP is unavailable, in order: (1) `rfcomm_channel_observed` from [models.toml](models.toml) for the model named by the BT device name (drop the 4-character suffix, then a trailing `_`); (2) channel 1; (3) channel 2.
  - A successful `connect()` does **not** prove the channel is right. On the E560BT and D610BT, channel 1 is Apple iAP: an RFCOMM connect to it succeeds ([zakx] opens it on purpose to prime the multiplexer), but it silently swallows all data [zakx `iobluetooth.py`]. Accept a candidate channel only after `ESC i S` on it returns a valid 32-byte `80 20 42` status within the read timeout; otherwise close it and try the next candidate.
- **Device identification:**
  - Class of Device: major class 6 (Imaging), minor "Printer". On the P710BT, CoD = `0x042680` [HW]. Brother's inquiry filter requires `deviceClassMajor == 6 && deviceClassMinor == 0x20` (IOBluetooth minor value) [MacSDK `isPrinter`].
  - Device name: the model followed by a 4-character suffix, e.g. `PT-P710BTxxxx` [HW], or with an underscore, e.g. `PT-E560BT_0334` [zakx]. Brother derives the model by dropping the last 4 characters and then a trailing `_` [MacSDK `modelNameInSPServiceRecord`].
  - If the device has an HCRP record (UUID `0x1125`), Brother reads the model name from SDP attribute `0x0302` of that record instead.
  - The authoritative model check is `st[4]` from the first status reply (§4).
- **Pairing:**
  - The device must be bonded at OS level before connecting [AndroidSDK `getBondedDevices`; Chromium Web Serial].
  - Brother uses Secure Simple Pairing with no PIN on macOS [MacSDK `BSMBluetoothPairingManager`, 10 s timeout]. Community projects use PIN `0000` when legacy pairing asks for one [Ircama, labellab].
  - Link security: [AndroidSDK] opens an **insecure** (unauthenticated) socket for PT-P300BT, PT-P710BT and PT-P715eBT (selected by exact model enum, so PT-P300BTz gets a secure socket), and a **secure** (authenticated, encrypted) socket for every other model [AndroidSDK `BluetoothConnection.prepareConnection`]. [MacSDK] opens the baseband with `authenticationRequired:NO` for every model.
  - **Conflict:** Android raises link security for "secure" models; macOS does not, and Brother's macOS app prints to them. **Resolution:** `bt_socket_security` in [models.toml](models.toml) is informational. Hosts use the OS default security on a bonded link (Linux: no `BT_SECURITY` sockopt; Windows: default `SOCKADDR_BTH` connect / plain `ConnectAsync`; macOS: `authenticationRequired:NO`), following the Brother macOS precedent. If a "secure" model refuses the connection or drops it on the first write, retry once with raised security (Linux `BT_SECURITY_MEDIUM`; WinRT `BluetoothEncryptionWithAuthentication`). UNVERIFIED on hardware (§9.2).
- **Single host:** the printer accepts one SPP connection at a time [labellab; Web Serial research, UNVERIFIED]. Close the connection when idle.
- **Writes:**
  - Flow control is RFCOMM credit-based. There is no software flow control and no inter-chunk delay. Brother sends a whole page (or job) as one logical write, chunked to the transport MTU [MacSDK `write:data:`; AndroidSDK 1000-byte chunks with `flush()`].
  - On macOS, each `writeSync` MUST be ≤ the channel MTU. The P710BT negotiated MTU is 320 [HW].
  - `getMTU()` can read 0 right after an async open [OpenSCQ30 macOS transport, via the transport research]. Brother's write loop has no guard for this and spins forever on zero-length writes [MacSDK `write:data:`]. If `getMTU()` returns 0, wait for `rfcommChannelOpenComplete:status:` and read it again; if it is still 0, use a conservative chunk of 320 bytes (measured P710BT MTU; [Ircama] uses 320, [zakx] 512, [vowstar] clamps to 1…1024). Never issue a zero-length `writeSync`.
  - A job that was partially written MUST NOT be re-sent blindly. Re-sending duplicates labels [esp32-ptouch, nbuchwitz PR#26]. Recovery is in §6.10.
- **Reads:**
  - On the print path (§3.1 commands) the printer only sends 32-byte status frames. Brother reads exactly 32 bytes per read, with a 10 s timeout [MacSDK `readData:`].
  - The optional §3.4 commands have other reply formats (16 bytes, a length byte plus ASCII, a DC1-framed reply, or an UNKNOWN layout). Send them only while idle, read their reply with a command-specific parser, and only then resume the 32-byte framer. A 32-byte framer fed such a reply desynchronises, and its `80 20 42` resync scan can match inside other data.
  - Implementations MUST handle partial reads and coalesced frames: accumulate bytes, and frame on 32-byte boundaries starting at the header `80 20 42` [vowstar reads up to 128 bytes; labelpi uses a read-exact loop].
  - On a header mismatch, resynchronise by scanning for `80 20 42`.
  - Some models emit an unsolicited status after `ESC i a 01` [ptouch-print `FLAG_P700_INIT` flushes one frame]. Drain the input before sending `ESC i S`, or parse every frame by its status type (§4.4).
- **Timing:**
  - Cold open plus first status: ~2.0 s on a P710BT; warm: ~0.4 s [HW]. A P300BT asleep takes 3–3.7 s [Ircama].
  - [AndroidSDK] sleeps `connectionWaitMSec` (500 ms) after `connect()` only when the device name matches `shouldWaitAfterConnection()`; among PT models that is names containing `PT-P300BT`, `PT-E550W` or `PT-P750W` (not P710BT, P910BT, E560BT, …).
  - After `close()` it always sleeps: `closeWaitMSec` (500 ms), or 3000 ms if an error occurred [AndroidSDK `closeConnection`].
  - **Resolution:** wait 500 ms after connect on every model, and 500 ms after close (3 s after an error).
  - [AndroidSDK] `TimeoutSetting`: send timeout 90 s, receive (per read) timeout 180 s.
- **Wake-up and first contact:**
  - BT links can be half-awake on first access. Community drivers retry {invalidate + `ESC @` [+ `ESC i a 01`] + `ESC i S` + read 32} 3–6 times [Ircama: 6, labelpi: 3].
  - **Resolution:** up to 3 attempts, each with a 5 s read timeout.

### 2.2 macOS (IOBluetooth)

Brother's own transport [MacSDK `BSMBluetoothDevice`], with the deviations this spec adopts marked as such. A Rust prototype on macOS 27.0.1 against the P710BT [HW] verified **only** steps 4–8 (cache/SDP channel lookup, sync/async open, `writeSync`, delegate read, `closeChannel`), and that prototype only ever wrote 5 bytes (`1B 40 1B 69 53`). Since then the `ptouch` CLI has printed a complete job on the P710BT ([HW] orientation test label, PT-P710BT, 24 mm TZe, 2026-10-08), but the [HARDWARE-TESTS.md](HARDWARE-TESTS.md) log does not record which transport it used; until it does, this section does not count that print as evidence for any step below. Steps 2, 3, 9 and 10 and the close/retry logic are **UNVERIFIED in Rust**. For multi-KB, MTU-chunked `writeSync` on the main thread, the evidence is [obwat] `scripts/hardware-debug/print_job.swift`, which printed a real label on a P710BT on macOS 26 this way.

1. **Discovery:**
   - First enumerate `+[IOBluetoothDevice pairedDevices]`, with no CoD filter.
   - Then optionally run `IOBluetoothDeviceInquiry` and keep devices with CoD major 6 / minor printer that have an SPP or HCRP SDP record.
   - Brother's inquiry (`handleMaybeIncompleteDeviceFound:`) calls `performSDPQuery:` for a found device without a cached record and reports it only from `sdpQueryComplete:status:`. On macOS 26/27 that delegate never fires (step 4), so newly discovered, unpaired printers never appear in Brother's list. **Deviation:** for inquiry results without a cached record, call `performSDPQuery:` and poll `getLastServicesUpdate` / `getServiceRecordForUUID:` (every 200 ms, ≤ 10 s), as in step 4.
2. **Pairing** (only if not paired): `IOBluetoothDevicePair`, 10 s timeout [MacSDK]. Brother waits only for `deviceSimplePairingComplete:status:`, so a printer that asks for a legacy PIN (community PIN `0000`) times out. **Deviation:** also implement `devicePairingPINCodeRequest:` → `replyPINCode:` with `0000`. On macOS 26/27 the pairing delegate is also delivered on the main queue (step 6). Rust: needs the `objc2-io-bluetooth` feature `IOBluetoothDevicePair`, which the prototype did not enable. UNVERIFIED.
3. **Baseband:**
   - If the device is not connected: `openConnection:nil withPageTimeout:0x2710 authenticationRequired:NO` (page timeout 6.25 s) [MacSDK].
   - Remember whether *this* code opened the baseband.
   - [zakx] reports that after a printer power cycle `isConnected()` stays true (macOS re-pages the baseband for iAP) although the old RFCOMM session is dead, so an open over that link fails or hangs (see step 9 for the recovery).
   - Rust binding: `IOBluetoothDevice::openConnection_withPageTimeout_authenticationRequired(target, u16, bool)` and `closeConnection()` exist in `objc2-io-bluetooth 0.3.2` (`IOBluetoothDevice.rs` l.813/828). UNVERIFIED in the prototype.
4. **Channel:**
   - Read `getServiceRecordForUUID:(uuid16 0x1101)` from the SDP cache.
   - If the record is absent, call `performSDPQuery:` and **poll `getLastServicesUpdate`** every 200 ms for up to 10 s.
   - On macOS 26/27, `performSDPQuery:` never calls its `sdpQueryComplete:status:` delegate (IOBluetooth logs "This currently won't trigger SDP delegate") [HW]. Brother's `BSMBluetoothDeviceResolver` polls its `completed` flag for 10 s (a delegate that never fires), then re-reads `getServiceRecordForUUID:` anyway [MacSDK `getSPPServiceRecord:queryIfNotQueried:`]. Brother's open therefore still works on macOS 26/27, only 10 s slower; polling `getLastServicesUpdate` avoids the delay.
   - Then call `getRFCOMMChannelID:`.
   - A cached record from before a printer power cycle can point at a stale channel; [zakx] always runs a fresh SDP query. **Resolution:** cache first (Brother); if the open in step 5 fails with the cached channel, run a fresh SDP query and retry once.
5. **Open:**
   - **Multiplexer priming** (step 10) first, when the SDP-resolved SPP channel is not 1.
   - Call `openRFCOMMChannelSync:withChannelID:delegate:`.
   - Brother falls back to `openRFCOMMChannelAsync:` on **any** non-zero sync result, `kIOReturnTimeout` included, then polls `openRFCOMMChannelCompleted` 50 × 200 ms [MacSDK `openSerialPort:reader:error:`].
   - **Deviation (this spec):** fail fast on `kIOReturnTimeout` (`0xE00002D6`: printer off or out of range) instead of falling back; on other failures fall back to the async open and wait ≤ 10 s for `rfcommChannelOpenComplete:status:`.
   - If the async open times out, close the half-opened channel (`closeChannel`) and the baseband (`closeConnection`) before any retry.
   - Do not trust `isOpen()`: it turns true before writes succeed.
6. **Threading (macOS 26/27):**
   - IOBluetooth is a shim over CoreBluetooth. It delivers **every** RFCOMM and inquiry delegate callback via `dispatch_async(main_queue)` [HW; IOBluetooth disassembly].
   - The **main thread MUST pump its CFRunLoop**. With a blocked main thread, both sync and async opens fail even though `bluetoothd` reports the channel connected [HW].
   - CLI design: run the IOBluetooth state machine on the main thread and the application on a worker thread. IOBluetooth objects are `!Send`.
7. **Write:** loop `writeSync:length:` in chunks of `min(remaining, mtu)`, where length is a `u16` and `mtu` follows the zero-MTU rule in §2.1. Retry on `kIOReturnNotOpen` (`0xE00002CD`) for up to ~2 s right after the open.
8. **Read:** append the bytes from `rfcommChannelData:data:length:` to a buffer, and consume 32-byte frames.
9. **Close:**
   - Brother: `setDelegate:nil`, then `closeChannel`; `closeConnection` on the device only if step 3 opened the baseband [MacSDK `closeSerialPort:`].
   - **Conflict:** three community macOS implementations differ. [Ircama] calls `closeChannel` with the delegate still set and pumps the run loop until `rfcommChannelClosed:` (≤ 1 s), calling this "the crux of the macOS reconnect bug". [vowstar] waits ≤ 1 s for the close callback, then calls `closeConnection` and pumps 250 ms; it reports that closing only the channel can leave the next open without an open-complete callback. [zakx] pumps after each step and releases the baseband on every close.
   - **Resolution:** call `closeChannel` with the delegate still set; keep pumping the main run loop until `rfcommChannelClosed:` arrives or ~1 s passes; only then clear the delegate. Call `closeConnection` if step 3 opened the baseband, **and** after any failed or timed-out open even when this code did not open the baseband (stale link after a power cycle, step 3). Pump the run loop ~250 ms after `closeConnection`. A CLI MUST NOT exit before this drain, or `bluetoothd` may never tear the link down.
10. **Multiplexer priming:**
    - On the E560BT, a direct open of the SPP channel (2) on a cold RFCOMM multiplexer stalls: the sync open returns `kIOReturnError` after ~3 s (not a timeout) and the async open's completion callback never fires [zakx]. Opening and closing channel 1 first makes channel 2 open immediately.
    - **Resolution:** prime unconditionally whenever the SPP channel is not 1, before every open attempt: open channel 1 synchronously, close it, pump the run loop ~300 ms, then open the SPP channel [zakx `_prime_mux`]. Waiting for a first failure instead costs > 13 s per cold connect (3 s sync error + 10 s async wait) and leaves a dangling async channel. UNVERIFIED on models other than the E560BT; harmless where channel 1 is the SPP channel (no priming then).
11. **Permissions (TCC):**
    - Bluetooth access is attributed to the responsible process. For a CLI that is the terminal application [HW: tccd `AUTHREQ_ATTRIBUTION responsible=…ghostty`].
    - Terminal.app's Info.plist on macOS 27.0.1 has no `NSBluetoothAlwaysUsageDescription`; Ghostty's has it [HW, `plutil -p`]. The prototype was only ever run from Ghostty. Whether a CLI run from Terminal.app can use Bluetooth is **UNVERIFIED** (test it); [zakx] (hardware-verified on macOS) only tells users to "grant your terminal Bluetooth permission if prompted".
    - User workaround: grant the terminal app Bluetooth access in System Settings › Privacy & Security › Bluetooth.
    - An embedded `__TEXT,__info_plist` section, ad-hoc re-signed, is only used when the binary is its own responsible process.
    - Ship end-user tools as a signed `.app`.
12. **`/dev/cu.<name>` serial node:**
    - **Conflict:** in one session on this Mac, opening `/dev/cu.PT-P710BTxxxx` raw and sending `00×100 1B 40 1B 69 53` returned a valid status in ~1 s [HW, hardware note]. In another session (macOS 27.0.1) the same node opened and accepted writes, but there was no RFCOMM connection attempt and no data [HW, transport prototype]. [Ircama] reports half-open hangs after the first close on P300BT. [zakx] reports that the E560BT node binds the iAP channel.
    - **Resolution:** IOBluetooth is the default macOS backend. The serial node is an opt-in fallback only.
13. Rust crates verified to compile and to run steps 4–8 [HW prototype]: `objc2 0.6.5`, `objc2-foundation 0.3.2`, `objc2-core-foundation 0.3.2`, `objc2-io-bluetooth 0.3.2` (features used: `Bluetooth`, `IOBluetoothObject`, `IOBluetoothDevice`, `IOBluetoothRFCOMMChannel`, `IOBluetoothSDPServiceRecord`, `IOBluetoothSDPUUID`, `IOBluetoothSDPDataElement`, `IOBluetoothDeviceInquiry`, `IOBluetoothUserLib`). Pairing additionally needs `IOBluetoothDevicePair` (untested). `IOReturn` is crate-private in `objc2-io-bluetooth`, so define the constants locally. The prototype maps `getMTU() == 0` to one 65535-byte write, which breaks the MTU rule in §2.1; do not copy that.

### 2.3 Linux (BlueZ)

- **Preferred:** a raw socket `socket(AF_BLUETOOTH=31, SOCK_STREAM, BTPROTO_RFCOMM=3)`. Call `connect()` with `sockaddr_rc { family, bdaddr (byte-reversed), channel }`, then use blocking `read`/`write` with `SO_RCVTIMEO` [labelpi; prototype compiles].
  - `sendall` of a whole job is fine, because the kernel handles RFCOMM credits [labelpi prints whole jobs this way].
- **Alternative:** `bluer 0.17.4` with feature `rfcomm` (no D-Bus): `rfcomm::Stream::connect`.
- **Channel lookup:** the raw socket has no SDP, so without a lookup it always uses the §2.1 fallback list. Two ways to get the channel from SDP:
  1. **BlueZ Profile API** via `bluer` with features `["bluetoothd", "rfcomm"]` and a running `bluetoothd`. `Device::connect_profile` takes a full `&Uuid`, not `0x1101`, and does not return a stream by itself. Flow: `session.register_profile(Profile { uuid: 00001101-0000-1000-8000-00805f9b34fb, role: Some(Role::Client), .. })` → `device.connect_profile(&uuid)` → `handle.next().await` (the `ConnectRequest` on the `ProfileHandle`) → `req.accept()` → `rfcomm::Stream`. BlueZ performs SDP and connects.
  2. **Raw SDP** without D-Bus: a `ServiceSearchAttribute` request for UUID `0x1101`, attribute `0x0004` (ProtocolDescriptorList), over L2CAP PSM 1 (the equivalent of libbluetooth's `sdp_service_search_attr_req`); the RFCOMM channel is the parameter of the RFCOMM protocol descriptor.
  - Without either, use the §2.1 fallback order (`rfcomm_channel_observed` for the model, then 1, then 2) and accept a channel only after a valid status reply. [labellab]'s BlueZ transport hard-codes channel 1 and is not hardware-tested.
- **`EBUSY`** on an immediate reconnect, while the previous RFCOMM link is still closing: retry for up to 5 s [labelpi].
- `/dev/rfcommN` (`rfcomm bind`, deprecated) works with the unchanged byte stream [nbuchwitz#18, ptouchgo]. Fallback only.
- `TIOCOUTQ` on an RFCOMM socket returns *free* space, not queued bytes [labelpi].
- Pairing: `bluetoothctl pair` and `trust`.

### 2.4 Windows

- **Preferred:** Winsock `socket(AF_BTH=32, SOCK_STREAM, BTHPROTO_RFCOMM=3)` with `SOCKADDR_BTH { btAddr, serviceClassId = SPP GUID, port = 0 }`. With port 0, Windows performs the SDP lookup itself. `SOCKADDR_BTH` is `packed(1)`, 30 bytes. Crate: `windows-sys 0.61.2` (`SerialPortServiceClass_UUID` must be defined locally). [Prototype compiles; UNVERIFIED on hardware.]
- **Alternative:** WinRT `RfcommDeviceService::FromIdAsync(id)` (enumerated with `RfcommServiceId::SerialPort`), then plain two-argument `StreamSocket::ConnectAsync(service.ConnectionHostName(), service.ConnectionServiceName())`, blocking with `.get()` on `windows 0.58` [labellab `ll-transport/src/bluetooth/windows.rs`; hardware-verified on a P710BT for a status query and a real 9 mm print].
  - `RfcommDeviceService` enumerates the P710BT under its SPP service name **"SPP SERVER"**, not the device name; identify it by the MAC in the device ID [labellab].
  - The `ConnectWithProtectionLevelAsync(..., BluetoothEncryptionAllowNullAuthentication)` variant with `windows 0.62` and `.join()` comes only from this project's prototype, which was type-checked but never run: **UNVERIFIED**.
- The virtual COM port ("Standard Serial over Bluetooth link"): results were mixed [labellab]. On 2026-10-01 a status query and a print over the outgoing BT COM port worked; later the same day, on the test PC, every outgoing port failed with `ERROR_SEM_TIMEOUT` in both .NET `SerialPort` and `tokio-serial`. Windows creates an Outgoing and an Incoming port; only Outgoing is usable. Fallback only.

### 2.5 Android (reference only)

[AndroidSDK] `BluetoothConnection`:

- Gets the device from `getBondedDevices()` by MAC.
- Creates an insecure or secure RFCOMM socket to the SPP UUID (§2.1) and cancels discovery before calling `connect()`. There is one attempt and no retry.
- Sleeps `connectionWaitMSec` (500 ms) after `connect()` only if the device name matches `shouldWaitAfterConnection()` (PT: P300BT, E550W, P750W).
- On close, always sleeps 500 ms, or 3000 ms if an error occurred.
- Writes in 1000-byte chunks, with `flush()` after each.
- Reads until the requested count arrives (32 for status).
- Timeouts (`TimeoutSetting`): 90 s per send, 180 s per receive.

### 2.6 Browser (Web Serial), for the `web/` studio

- Chromium 117+ (desktop) and Chrome Android 138+ open RFCOMM directly:
  ```
  const SPP = "00001101-0000-1000-8000-00805f9b34fb";
  navigator.serial.requestPort({
    filters: [{ bluetoothServiceClassId: SPP }],
    allowedBluetoothServiceClassIds: [SPP],   // not optional in practice (ARCHITECTURE.md §3.2)
  })
  ```
  The printer must be OS-paired.
- **Conflict (negative hardware report):** [obwat] tested Chrome 150/151 on macOS 26 with a PT-P710BT. The chooser listed "PT-P710BT3867 – Paired", but `port.open()` failed with "Failed to open serial port" (2026-07-18). **Resolution:** treat Web Serial over Bluetooth on macOS as **known-failing** until it is tested on the user's machine; WebUSB is the working browser path on macOS [obwat]. Other platforms: UNVERIFIED.
- `open({ baudRate })` requires a baud rate, but the value is ignored. Use `flowControl: "none"`.
- After `open()`, call `port.setSignals({ dataTerminalReady: true, requestToSend: true })` (SHOULD; wrap in try/catch). On Chromium's direct-RFCOMM port it is a no-op that returns success [Chromium `bluetooth_serial_port_impl.cc`]; on OS-mapped serial nodes it is needed, because the P300BT "stays silent" until DTR/RTS are asserted [Ircama `web/printer.js`, labelartor `web-serial.ts`].
- Calling `requestPort()` with no filters additionally lists OS-mapped nodes (`/dev/cu.*`, COMn, `/dev/rfcommN`).
- Web Bluetooth cannot reach SPP printers (it is GATT-only). It is relevant only to PT-N25BT (§2.7).
- Safari/iOS has neither Web Serial nor WebUSB.
- [Web research; no successful end-to-end Web Serial print with a P-touch is known.]

### 2.7 Bluetooth Low Energy (PT-N25BT only)

[AndroidSDK `BLEConnection`; MacSDK has the same framing in shared C++ but no CoreBluetooth, so macOS P-touch Editor cannot use the N25BT.] Entirely **UNVERIFIED** on hardware.

| Item | UUID |
|---|---|
| Service (scan filter) | `A76EB9E0-F3AC-4990-84CF-3A94D2426B2B` |
| E1: read (polled) | `A76EB9E1-…` |
| E2: write with response; also used to force pairing | `A76EB9E2-…` |
| E3: write-without-response + notify (flow-control acks) | `A76EB9E3-…` |
| E4: notify (printer → host data) | `A76EB9E4-…` |

1. Connect GATT over the LE transport. Allow up to 3 attempts, each with a timeout of max(5000 ms, configured).
2. Request MTU 512. Fall back to 23 if the request fails.
3. If E3 exists: write with E3 and enable its notifications; force pairing by writing `00` to E2 (with response, 60 s timeout). Otherwise write with E2.
4. Read from E4 (notifications) if present, otherwise poll E1. GATT status 128 on E1 means no data yet, so read again. Reads come in 32-byte units.
5. **E3 framing:**
   - `D = MTU − 5`. Split the payload into packets of ≤ `D×8 − 4` bytes.
   - Prefix each packet with `06 F0 NN 00`, where `NN = ceil((len+4)/D)` is the number of ATT writes that follow.
   - Write the header plus packet in ATT writes of ≤ `D` bytes.
   - Then wait for an E3 notification: `06 F0 01` means OK, `06 F0 02` means error. The timeout is 3 s, or 10 s if the total exceeds 1024 bytes.

### 2.8 USB

[D1/D2/D3 Appendix A]

- VID `0x04F9`. Printer class, full speed, one interface.
- **Bulk OUT EP `0x02`** (data), **bulk IN EP `0x81`** (status). Max packet size 64.
- The serial-number string descriptor is `"000"` + the last 9 digits of the serial [D1, D2]. [D3] (H500/P700/E500) differs: its example is `"000000001"`, described only as "last nine digits of the printer's serial number", with no `000` prefix. Do not parse the descriptor; identify the model by PID and `st[4]`.
- PIDs are in [models.toml](models.toml).
- Editor Lite / mass-storage mode exposes a different PID (PT-P700 `0x2064`, PT-P750W `0x2065`) and does not accept raster data. The user must switch Editor Lite off [ptouch-print, nbuchwitz#32].
- **Writes:** [ptouch-print] writes ≤ 128 bytes per bulk transfer; [treideme] writes 64-byte chunks with a 15 s timeout; [esp32-ptouch] sends the whole P710BT job in one transfer. While printing, the printer back-pressures bulk OUT for roughly the print duration [nbuchwitz PR#26]. Use long write timeouts (≥ 30 s) and never auto-retry.
- **Status:** poll bulk IN, e.g. every 100 ms, until 32 bytes arrive [ptouch-print].
- **Concurrent printing**, where the printer starts before the whole page arrives, happens only on USB with uncompressed data [D1–D4 §1]. Every other combination is buffered.
- On E560BT/E310BT, a job left unterminated (missing `n9=2`) survives a power cycle and blocks USB OUT [teip, ptouch-print commit 1f450d9].

### 2.9 TCP port 9100 (Wi-Fi/Ethernet models: E550W, P750W, P900W, P950NW, D800W, E800W, E850TKW)

- Send the same byte stream to TCP 9100 [Brother developer FAQ].
- **Status:**
  - Brother's Android SDK reads status over SNMP OID `1.3.6.1.4.1.2435.3.3.9.1.6.1.0`, which returns the same 32 bytes [Brother FAQ, AndroidSDK].
  - MacSDK sends `ESC i S` on the network port and polls with `sleep(1)`.
  - [brother_ql]'s network backend never reads back.
  - Whether the 32-byte status can be read back on the TCP 9100 socket is **UNKNOWN**. Implement SNMP as the primary status path for network printers.

#### 3.2.1 `ESC i z` print information: `1B 69 7A n1 n2 n3 n4 n5 n6 n7 n8 n9 n10`

- **n1 valid flags** [D1–D4]:
  - `0x02` PI_KIND (n2 valid), `0x04` PI_WIDTH (n3 valid), `0x08` PI_LENGTH (n4 valid), `0x40` PI_QUALITY (D1: "not used"), `0x80` PI_RECOVER ("printer recovery always on"; on P900/P900W/P950NW it also enables status notification during printing, but not on P910BT [D2]).
  - [D4] marks `0x40` and `0x80` as "Not used" for E310BT/E510/E560BT, yet its own driver dump sends `0x84`.
  - When KIND/WIDTH/LENGTH are flagged and the loaded media does not match, the printer answers with an error status, `st[9] = 0x01`.
  - Observed values: `0x84` in every Brother driver dump [D1–D4 dumps; esp32-ptouch, verified on P710BT]. The SDK computes `0x80 | 0x04 | (0x02 if media type ≥ 2 or high/low-res) | (0x40 unless double-speed quality)`, typically `0xC4` [SDK]. `0x00` is used by the "D460 dialect" [ptouch-print, zakx, teip].
  - **Resolution:** `0x84`. Add `0x02` when n2 carries a type the printer must check: heat-shrink `0x11`/`0x17`, FLe `0x13`, or the high-res/draft alternate `0x09`. Never set `0x08` (the SDK never does for PT).
- **n2 media type:**
  - Values: `00` (D1/D3: no tape; D2: "laminated/non-laminated tape"; D4: "laminated / self-laminated tape"), `01` laminated, `03` non-laminated, `09` laminated tape in high-resolution **or draft** mode (D2: P900/P900W/P950NW "high-resolution printing and draft printing are supported for laminated tape only. Please set to 09h"; D4: E510/E560BT high-res; SDK also uses it for 128-pin TZe in high-res), `11` heat-shrink 2:1, `13` FLe, `17` heat-shrink 3:1, `FF` incompatible.
  - The SDK sets n1 `|= 0x02` and n2 = the paper's alternate type (`0x09` for laminated TZe) whenever high **or low** resolution is active [MacSDK `setPrintInformation`].
  - The SDK sends the paper-table value: `01` for TZe on 128-pin/P300BT/N25BT lists, `00` for TZe on 560-pin lists. Ignored unless `n1 & 0x02`. Per-media values are in [models.toml](models.toml) (`print_info_media_type`).
- **n3** width in mm: the same value the status reports in `st[10]` (3.5 mm → 4).
- **n4** length in mm: `00` for continuous tape; 45 for FLe.
- **n5–n8** number of raster lines in this page (count of `G` + `Z` lines actually sent), LE32. In high-res mode this count is already doubled.
- **n9 page position:**
  - `00` first page, `01` other pages. On `start_next_end` models, `02` marks the last page, and a single-page job sends `02` [D2 §2.3, D4, SDK].
  - On `start_end` models (P300BT, P710BT, P715eBT, E720BT, E550W, P750W, P700, H500, E500, D450, D600), n9 is never 2 [SDK; D1 dump sends 0 then 1].
  - Omitting `02` on an E560BT leaves it stuck in "printing", and the job survives a power cycle [teip].
- **n10:** `00`. The SDK sends `01` ("energy up") only with high-res plus threshold halftone. **Resolution:** always `00`.

#### 3.2.2 `ESC i M` various mode: `1B 69 4D n`

| Bit | Mask | Meaning | Models |
|---|---|---|---|
| 6 | `0x40` | Auto cut | All models with a cutter. On PT-P300BT/P300BTz/N25BT (no cutter) the same bit means **print cut marks** [SDK `CUTMARK`]. |
| 7 | `0x80` | Mirror printing | Models with SDK `MIRROR`. **Conflict:** [D4] documents bit 7 "Mirror printing" for E310BT/E510/E560BT without any model exception, but the SDK `VariousMode` for those models (and D410/D460BT/D610BT) lacks `MIRROR` and never sets it. **Resolution:** on those six models hardware mirror is *documented (E-series) but unverified*; the library mirrors in software by default (`supports_mirror = false`). |
| 4 | `0x10` | Peel (SDK `PEEL`) | Not used by any PT model. |
| 0–5 other | – | Unused or reserved | Send 0. |

[zakx] reports that on the E560BT, `ESC i M 40` forces a full cut on every page, even alongside `ESC i K 04`. [teip] sends `ESC i M 40` only on the first page, to cut off the blank leader.

#### 3.2.3 `ESC i K` advanced mode: `1B 69 4B n`

| Bit | Mask | Meaning | Notes |
|---|---|---|---|
| 0 | `0x01` | Draft / low-resolution printing | P900/P900W/P950NW [D2]; also D800W/E800W/E850TKW [SDK `LOW_RESOLUTION`; PTD resolution list includes 360×180]. MUST be 0 on P910BT [D2] and E920BT (no SDK `LOW_RESOLUTION`). Laminated tape only; send `ESC i z` n1 `|= 0x02`, n2 = `0x09` (§3.2.1). |

| 4 | `0x10` | Special tape: no cutting | SDK `SPECIALTAPE`. The SDK *assigns* `n = 0x10`, which clears the other bits; for PT-P710BT and P715eBT it assigns `0x18` [SDK]. |
| 5 | `0x20` | "Label cut end" | SDK `LABEL_CUTEND` (P900W/P950NW/D800W/E800W/E850TKW only). Docs: "not used". Semantics **UNKNOWN**. |
| 6 | `0x40` | High-resolution printing (180×360 or 360×720) | Models with `supports_high_resolution`. MUST be 0 on P910BT and E310BT [D2, D4]. |
| 7 | `0x80` | No buffer clearing when printing | D1–D3. The SDK never sets it. Do not use. |

#### 3.2.4 `ESC i d` margin: `1B 69 64 nL nH`

- The value is in dots of the **feed-direction** resolution: ×2 in high-res, ×0.5 in low-res [D1 §2.3.3, SDK].
- Default: 14 dots, which is 2 mm at 180 dpi and 1 mm at 360 dpi. The default is 28 dots for heat-shrink on 560-pin heads, and 70 for FLe [SDK paper tables].

| Group | Min | Max |
|---|---|---|
| 180×180 | 14 | 900 |
| 180×360 | 28 | 1800 |
| 360×360 | 14 | 1800 |
| 360×720 | 28 | 3600 |

[D1 §2.3.3, D2, D4]

- Several community drivers send `00 00` and print fine on P710BT/P300BT [esp32-ptouch, labelpi, vowstar, robby]. The printer appears to clamp the value. **Resolution:** default to 14 (or the media's `default_feed_dots`), and allow 0.

### 3.3 Protocol-version gates (SDK `bpes::CommandProtocol`)

`protocol_version` defaults to 89. Exceptions: P910BT and E920BT = 92; E310BT, E510 and E560BT = 93; D410, D460BT and D610BT = 94; N25BT = 105.

| Feature | Condition |

| `ESC i z` (instead of legacy `ESC i c`) | v > 88: all models in scope |

| `ESC i L 00 01 01` + `ESC i C 01 FF FF FF` | v ∈ {93, 94} or v > 104 |
| Custom record `1B 69 11 53 64 01 <len ≤ 64> <data>` | v > 105: none |

Two community conventions are **wrong** and MUST NOT be copied:

- [Ircama]/[zakx] swap bytes 6 and 7. **Resolution:** follow [D2]/[D4] and [SDK]: byte 6 = battery, byte 7 = extended error.
- [ptouch-print] reads bytes 8–9 as one little-endian u16, while [Ircama]/[labelpi] read them big-endian. **Resolution:** two independent bytes.

Other projects with broken maps: [rust-ptouch] (model taken from `r[0]`, phase type from `r[20]`) and [the78mole] (whole map).

Validation [SDK `checkPrinter`]:

- `st[0..3] == 80 20 42` (otherwise "not a Brother printer").
- `st[3]` = the expected series.
- `st[4]` = the expected model (otherwise "not the target printer").

```

### 4.2 Status type `st[18]`

| Value | Meaning | Handling |
|---|---|---|
| `00` | Reply to a status request | Inspect errors, media and phase |
| `01` | Printing completed | Page done |
| `02` | Error occurred | Decode §4.5; the printer has discarded its buffer |
| `03` | Exit IF mode | Not used; treat as unexpected |
| `04` | Turned off | D4: not used. [Ircama] treats it as failure. Treat as fatal. |
| `05` | Notification | Decode `st[22]` |
| `06` | Phase change | Decode `st[19..21]` |
| `07`–`20` | Not used | – |
| `18` | Undocumented | **Conflict:** [MacSDK] `checkStatus` routes `0x18` to the `02` branch (`getErrorInfo`) [@0x13d474]; [AndroidSDK] native `checkStatus` logs 3, 4 and 7…`0x18` as "Unexpected status value" with `ERROR_COMMUNICATION_ERROR`. **Resolution:** either way it is an error; handle it as `02`. |
| `21`–`FF` | Reserved | Unexpected |

Protocol version 91 only: any non-zero `st[8]`/`st[9]` means error, whatever the status type [SDK]. [MacSDK] `checkStatus` also runs `getErrorInfo` (bytes 8, then 9, then 7) after a type-`00` reply [@0x13d474 → @0x13b18c]. **Resolution:** evaluate all three error bytes, `st[7]`, `st[8]` and `st[9]`, on **every** frame, type `00` included, and treat any non-zero value as an error whatever `st[18]` says. Some errors are reported only in `st[7]` (§4.5.3: `1D`, `1E`, `21`, `27`).

### 4.3 Phase `st[19]`, `st[20..21]`

| Phase type | Number | Meaning |
|---|---|---|
| `00` editing / receiving | `0000` | Ready to receive |
| | `0001` | Feeding (D1–D3) |
| `01` printing | `0000` | Printing |
| | `000A`, `0019` | Not used |
| | `0014` | Cover open while receiving: an error [SDK] |

"Ready" predicate:

```
st[7] == 0 && st[8] == 0 && st[9] == 0 && st[19] == 0 && st[20..22] == 00 00
```

[Ircama, zakx, labelpi; `st[7]` added per D2/D4 and MacSDK `getErrorInfo`, §4.2]. On D1/D3 models `st[7]` is documented as reserved `00`, so the extra test is harmless there.

### 4.4 Notification `st[22]`

| Value | Meaning |
|---|---|
| `00` | Not available |
| `01` | Cover open (SDK treats as error) |
| `02` | Cover closed |
| `03` | Cooling started; printing pauses, so extend timeouts |
| `04` | Cooling finished |

## 5. Raster encoding

### 5.1 Pin numbering and bit order (normative)

- A raster line is `bytes_per_line = head_pins / 8` bytes: 16 for 128 pins, 70 for 560 pins, 8 for 64 pins.
- **Head pin numbering:** pin 0 is the **least-significant bit of the last byte** of the line, and pin `head_pins − 1` is the **most-significant bit of byte 0**. Equivalently, the transmitted bit `t` (where `t = 0` is the MSB of byte 0, counting MSB-first through the bytes) drives pin `head_pins − 1 − t`.
- The media tables give, in pin numbers:
  - left margin: pins `[0, left)`;
  - print area: pins `[left, left + print)`;
  - right margin: pins `[left + print, head_pins)`.

So the transmitted line is *right margin → print area → left margin*.

Evidence:

- [D1] §2.3.5 figure (doc p.20, PDF p.24): the first byte of a line is at the right-margin end, and the last byte is at pin 0 / the left-margin end. Supports this convention.
- [SDK] `createTiffData`: the image row is written MSB-first at bit offset `left` into a zeroed head buffer, then the whole line is reversed (`out[W−1−i] = bitrev8(in[i])`). Supports this convention.
- [ptouch-print]: hardware-verified on a PT-P900Wc with 36 mm tape (`pin_offset` −8, print area centred on pin 272; narrower widths untested). It sets `rasterline[(size−1) − p/8] |= 1 << (p % 8)` [`ptouch-print.c:181`]. Applied to 24 mm on a 560-pin head, the same rule places data in transmitted bits 128…447, i.e. transmitted bytes 16–55, matching left = 112, right = 128. Supports this convention.
- **Against:** the "Explanation of TIFF compression mode" figure in [D1] (doc p.36, PDF p.40), repeated in [D2] (doc p.39) and [D4] (doc p.45), draws "0 pin" next to the **first** byte, then "number of offset pins", the print area, and "number of unused pins" at the last byte.

**Conflict:** Brother's own documents contradict themselves: the §2.3.5 figure puts pin 0 at the last byte, the TIFF-mode figure puts pin 0 at the first byte. The TIFF figure matches the [teip]/[nbuchwitz] convention "MSB of byte 0 = pin 0, data starts at bit `left`". The two conventions are identical for symmetric 128-pin tables except for a flip across the tape; on the asymmetric 560-pin tables they differ by 16 pins. **Resolution:** the convention above (pin 0 = LSB of the last byte). Tie-breakers: the SDK's explicit bit reversal in `createTiffData` and [ptouch-print]'s hardware result on 560-pin heads.

Image mapping:

- Let image pixel `p` (0 ≤ p < print) be the p-th pixel of the current image column across the tape.
- The SDK puts pixel `p` at pin `left + p`, i.e. transmitted bit `right + (print − 1 − p)` [AndroidSDK].
- Physical edge (**verified on PT-P710BT**, [HW] orientation test label, PT-P710BT, 24 mm TZe, 2026-10-08): image pixel `p = 0` (pin `left`; pin 0 on 24 mm) is the **top edge** of upright text, and `p = print − 1` the bottom edge. So a canvas row `y` (row 0 at the top) is image pixel `p = y`, and no flip across the tape is needed. The other models are assumed to match (same mechanism family) but have not been tested.

Content outside the print area must be zero. [vowstar] rejects P300BT data outside bytes 4–11. Data outside the area may trigger `st[9] = 0x01` [ptouch-print #21, UNVERIFIED].

Worked example: P710BT, 12 mm TZe (left 29, print 70, right 29), with a column where every print pixel is black.

- Pins 29–98 are set, so transmitted bits 29–98 are set.
- Line: `00 00 00 07 FF FF FF FF FF FF FF FF E0 00 00 00`.
- PackBits: `FE 00 | 00 07 | F9 FF | 00 E0 | FE 00` (10 bytes).
- Command: `47 0A 00 FE 00 00 07 F9 FF 00 E0 FE 00`.

Worked example: P910BT, 24 mm (left 112, print 320, right 128).

- Bytes 0–15 are the right margin (pins 559…432) and are always 0.
- Bytes 16–55 carry the 320 print pins.
- Bytes 56–69 are the left margin (pins 111…0).

### 5.3 Orientation, mirror and feed direction

- **First raster line = right end of the label when reading** (normative; hardware-verified on PT-P710BT only: [HW] orientation test label, PT-P710BT, 24 mm TZe, 2026-10-08). Lines are printed in the order received, and the first `G`/`Z` line of a page ends up at the **right-hand** end of the label held with the text upright (the end where reading stops); the last line is the left-hand end.
  - Evidence: the §9.1 orientation label was sent with canvas column 0 ("START", start of the arrow) as the first raster line. The pin axis was correct (row-0 line and short thick bar on the top edge, "START" above "F R 7", bottom bar at the bottom), but along the tape it was mirrored: "START" read mirrored at the right end and the arrow pointed left.
  - Consequence: to print a normal left-to-right image, send its columns **last column first**. The `ptouch` core does this in the encoder (`ModelProfile::feed_order()` = `FeedOrder::LastColumnFirst`), so pages handed to it are plain left-to-right canvases; the virtual printer and `decode` undo the order, so a decoded page reads like the printed label.
  - Every PT model in [models.toml](models.toml) uses the same convention: they share the mechanism (head across the tape, tape fed past the head towards the cutter), but only the P710BT has been tested. If another model is found to differ, give it its own `feed_order`; nothing else changes.
  - Short pages are padded at the canvas end (§5.6), i.e. at the right end of the label, so the padding lines are the first lines sent.
- The bit reversal in §5.1 is part of normal encoding. It is unrelated to `ESC i M 0x80`, which is a user-selectable mirror (for printing on the back of clear tape). With the order above, `ESC i M 0x80` gives the mirror image of the readable label.
- On models without SDK `MIRROR` (the D4/D-series 128-pin models), mirror in software: pad a page shorter than the minimum (§5.6) at its end first, then reverse the canvas left↔right before encoding. With the order above, the lines then go out in canvas order and the label is the exact mirror image of the readable one, with the padding at the left end. (Reversing before padding would leave the padding at the right end in both prints, which is not a mirror; the `ptouch` core's `prepare_pages` pads first.)

### 5.4 Resolution

- Normal: 180 dpi (head) × 180 dpi (feed) on 128- and 64-pin heads; 360 × 360 on 560-pin heads.
- High-res (`ESC i K 0x40`): feed resolution doubles (180×360, 360×720). Pins are unchanged. Send twice as many lines, double `ESC i d`, and set n5–n8 to the doubled count [D1, D2, SDK]. Hi-res mode:
  - is allowed only on laminated TZe;
  - on some models requires the AC adapter (extended error `1D`);
  - the SDK additionally sets `ESC i z` n1 |= `0x02` and n2 = `0x09` [SDK; D2/D4 for P900 family and E510/E560BT; **UNVERIFIED** for P710BT].
- [nbuchwitz] implements high-res by sending each line twice.
- Low-res/draft (`ESC i K 0x01`): P900/P900W/P950NW [D2]; also D800W/E800W/E850TKW [SDK `LOW_RESOLUTION`, PTD 360×180]; never P910BT/E920BT. It halves the feed resolution (360×180): send half as many lines, halve `ESC i d` and set n5–n8 to the halved count [SDK ×0.5]. Like high-res it is laminated-tape only and needs `ESC i z` n1 `|= 0x02` and n2 = `0x09` [D2 ESC i z note; SDK].

### 5.5 Compression

- `M 02` selects TIFF PackBits; `M 00` selects none.
- **Uncompressed (`M 00`):**
  - every line MUST be `47 W 00` followed by exactly W bytes (W = 16, 70 or 8);
  - `Z` is not allowed; send blank lines as `47 W 00` + W zero bytes [D1–D4, SDK `createRawData`].
- **PackBits (`M 02`)**, per line:
  - Encode the **full** W-byte line, including margins. Trailing zeros cannot be omitted [D1–D4].
  - Repeat run of c bytes (2 ≤ c ≤ 128): header `(1 − c)` as `i8` (`0xFF`…`0x81`), then the byte. Literal run of c bytes (1 ≤ c ≤ 128): header `c − 1` (`0x00`…`0x7F`), then the bytes. Never emit `0x80`.
  - If the encoding is longer than W bytes, send one literal run instead: `47 (W+1) 00 (W−1) <W bytes>` (17 bytes of data for W = 16, 71 for W = 70) [D1, SDK].
  - An all-zero line MAY be sent as `5A` [SDK uses `Z` for every blank line in TIFF mode] or as `47 02 00 (1−W) 00` (`47 02 00 F1 00` for W = 16; `47 02 00 BB 00` for W = 70) [driver dumps use both].
  - The G length field is the compressed byte count, LE16.
- Doc example (W = 16): `00×8 22 22 23 BA BF A2 22 2B` encodes to `F9 00 FF 22 05 23 BA BF A2 22 2B` [D4].
- Per-model default (`default_compression` in models.toml):
  - **PackBits** for P710BT, P715eBT, P300BT, P910BT and the USB/Wi-Fi siblings [D1/D2 dumps; esp32-ptouch, labelpi, Ircama, stecman capture].
  - Uncompressed `M 00` has also been verified on P300BT [vowstar] and P710BT [rust-ptouch, labelo].
  - **Conflict (E560BT family):** Brother's [D4 dump] and both SDKs send `4D 02` with PackBits to E310BT/E510/E560BT. The SDK also uses `COM_TIFF` for D410/D460BT/D610BT. However, [teip] (hardware) reports that PackBits gives **blank tape** on the E560BT, and [zakx] (hardware, E560BT) and [ptouch-print] send these models uncompressed. **Resolution:** default to `M 00` for D410, D460BT, D610BT, E310BT, E510 and E560BT. `M 02` remains selectable and is the first thing to test on hardware.
  - [ptouch-print] uses "fake compression" (`47 11 00 0F <16 bytes>`, one literal run) on PackBits devices. It is valid but gains nothing.
- PT-E550W reportedly requires compression **on** for the cutter to fire [nbuchwitz, rust-ptouch#31, UNVERIFIED].
- PT-N25BT: `COM_RAW` only, i.e. `M 00` with 8-byte lines [SDK].

| Group | Min print-data length (incl. both margins) | Max | Heat-shrink |
|---|---|---|---|
| D1/D3 180×180 | 4.4 mm = 31 dots | 7086 (1000 mm) | min 4.4 mm, max 3543 (500 mm) |
| D1 180×360 | 4.2 mm = 60 dots | 14172 | – |
| D2 360×360 | 4 mm = 57 dots | 14173 | min 4.2 mm = 60, max 7087 |

[D1 §2.3.4, D2 §2.3.4, D3 §2.3.4, D4 §2.3.4]

- These minimums are **not** a minimum number of raster lines. D1/D3 define them as "minimum print data length: 2 mm margins × 2 + minimum print area" [D1 §2.3.4 p.18]; D2/D4 use the same wording without the explicit formula.
- The SDK checks `lines × 254 / ydpi + 2 × MinMargin ≥ MinPrintPaperLength`, all lengths in 0.1 mm units, with `MinMargin` = 20 (2.0 mm) and `MinPrintPaperLength` = 44 (4.4 mm) for D410/D460BT/D610BT and 48 (4.8 mm) for E310BT/E510/E560BT [SDK spec tables]. For every other model the SDK has 0 (= not checked; for the P710BT D1 nevertheless gives 4.4 mm).
- **Resolution:**
  - `min_length_mm` in [models.toml](models.toml) holds this Brother/SDK minimum. Where it is unknown (no Brother doc and SDK 0, e.g. P300BT, N25BT, E720BT), use **4.8 mm**, the largest documented value.
  - Minimum raster lines: `min_lines = max(1, ceil((min_length_mm − 2 × margin_mm) × feed_dpi / 25.4))`, where `margin_mm` is the `ESC i d` value actually sent, converted to mm (the default 14 dots at 180 dpi ≈ 2.0 mm, the SDK's `MinMargin`). With the default 14-dot margin: 3 lines for 4.4 mm and 6 lines for 4.8 mm at 180 dpi; on 560-pin heads 14 dots at 360 dpi is only ≈ 1 mm per margin, so 4.0 mm needs `ceil((4.0 − 2 × 0.99) × 360 / 25.4)` = 29 lines. With margin 0, the whole minimum must be raster lines (31 / 34 / 57).
  - Pad short pages with blank lines up to `min_lines` (the `ptouch` encoder pads at the canvas end, i.e. the right end of the label, which is sent first; §5.3). A conservative mode MAY pad to the full documented dot count (31 / 34 lines at 180 dpi), as [zakx] does for the E560BT (34 lines); this only adds about 4 mm of blank tape.
  - `editor_min_label_mm` (PTD) is P-touch Editor's UI limit. On P300BT (25 mm) and N25BT (26 mm) it includes the ~25 mm leader; it MUST NOT be used to pad raster data, or short labels come out at roughly twice the expected length.
- Physical minimum label: the tape between head and cutter is always fed: ≈ 24.5 mm (128-pin), 27 mm (560-pin), 24.7 mm (D4) [D1–D4]. Data shorter than that still produces a label of that length.
- P300BT: ~25 mm leader before the print and ~1 mm after; max printable length 0.499 m [vowstar, Ircama; PTD max 500 mm].

### 5.7 Two-colour

No PT model in scope supports two-colour printing. Every SDK spec is `MONO_COLOR`.

- The QL-series `w` command (`77 c n data`, c = 1 black / 2 red) is not defined in any PT document.
- D4's `ESC i L` / `ESC i C` carry a red/black option, but "E310BT/E510/E560BT do not support red/black printing" [D4].
- **Resolution:** `supports_two_color = false` for all models; send only the mono `ESC i L 00 01 01` / `ESC i C 01 FF FF FF` where gated (§3.3).

## 6. Print job sequence

### 6.1 Pre-flight (once per connection)

1. Open the transport (§2).
2. Send `00×null_bytes`, then `1B 40`.
3. Send `1B 69 61 01`. Drain any unsolicited frame for ~100 ms.
4. Send `1B 69 53` and read 32 bytes, with a 5 s timeout and up to 3 attempts (§2.1).
5. Validate the header; identify the model from `st[3]`/`st[4]`.
6. Refuse to print if:
   - `st[7]`, `st[8]` or `st[9]` ≠ 0;
   - `st[11]` ∈ {`00`, `FF`};
   - `st[19..21]` ≠ `00 00 00` (not ready);
   - `st[10]` (plus the type) does not match the job's media (geometry lookup §4.6.1).

### 6.2 Recommended byte sequence (generic)

The order below follows Brother's driver dumps [D1, D2, D4]. The SDK orders `ESC i a 01` before `ESC @`, and `ESC i K` before `ESC i M`; both orders are reported to work. **Resolution:** follow the driver dumps, which match the hardware-verified [esp32-ptouch] P710BT stream.

```
-- job start --
00 × null_bytes
1B 40                                   ESC @
1B 69 61 01                             raster mode
[1B 69 21 00]                           if supports_status_notify (first page; MAY repeat per page)
-- per page i of N --
[1B 69 61 01]                           pages > 1: repeat (as the driver dumps do)
1B 69 7A n1 n2 <w> 00 <lines32> n9 00   §3.2.1
1B 69 4D <M>                            0x40 auto-cut (or cut-mark), |0x80 mirror if supported
[1B 69 41 <k>]                          if auto-cut && supports_cut_every (never P710BT/P715eBT)
1B 69 4B <K>                            §3.2.3

### 6.3 PT-P710BT (primary target)

The model is `start_end`, 128 pins, 100 null bytes, PackBits. It supports `ESC i !` but not `ESC i A` or half cut. Single label, 24 mm TZe, auto-cut, cut at end:

```
00×100
1B 40
1B 69 61 01
1B 69 21 00
1B 69 7A 84 00 18 00 <lines LE32> 00 00
1B 69 4D 40
1B 69 4B 08
1B 69 64 0E 00
4D 02
{ 47 nL nH <PackBits of 16 bytes> | 5A } × lines
1A
```

Sources and verification:

- This is byte-identical to the [esp32-ptouch] hardware-validated stream, except that the margin there is `00 00`.
- It matches [D1 dump] except that the dump has `ESC i ! 01` and `ESC i U J`.
- [treideme] and [robby] use the same structure.

For multi-page jobs:

- Each page ends with `0C` and the last with `1A`.
- n9 = 0 on page 1 and 1 afterwards.
- Pages ≥ 2 repeat `1B 69 61 01 … 4D 02` [D1 dump].
- Special tape (fabric etc.): `1B 69 4B 18` [SDK].
- High-res: `1B 69 4B 48`, `ESC i z` n1 = `86` and n2 = `09` (UNVERIFIED), doubled lines and margin.
- Expected statuses after `1A`: phase change (`06`, phase `01`), then `01` printing completed, then phase change (`06`, phase `00`) [D2 flow; P710BT behaviour per esp32-ptouch, treideme, vowstar].
- `1B 69 61 FF` at the end: the SDK sends it, the [D1 dump] does not. Optional.

None of these sources re-sends invalidate + `ESC @` per label: [zakx] calls `_reset()` (invalidate, `ESC @`, `ESC i a 01`) once before its page loop, and [teip] puts `00×100 1B 40` once at the start of each job group.

- **Conflict (multi-label):** the SDK uses `0C` between pages and n9 0/1/2. The community sends every label as its own page with n9 = 2 and `1A`. **Resolution:** default to one page per label with n9 = 2 and `1A` (hardware-verified), with the full control block repeated per label. Brother's `0C` / n9 = 1 form is UNVERIFIED.
- Cutting [zakx, teip]:
  - Never combine `ESC i M 40` with half-cut-only intent: it forces a full cut on every page.
  - Every page needs its own `ESC i K`. A page without one does not cut reliably after an earlier chained page.
  - The next job releases a chained (held) label with a full cut.
- [ptouch-print] and [esp32-ptouch] use margin 1 (`64 01 00`), and [zakx]/[teip] use 14. Both reportedly work. **Resolution:** 14.
- The D460-family chain packet `1B 69 4B 00 00` in [ptouch-print]/[vowstar] carries an accidental trailing NUL. Send `1B 69 4B 00`.
- Status:
  - Community reports say the E560BT pushes **no** status while printing, so it must be polled; it is busy ≈ 2.2 s even for an 8 mm label, which is why [ptouch-print] uses a 10 s minimum timeout.
  - Those implementations never send `ESC i ! 00`, and D4 says the default is "do not notify".
  - **Inference (UNVERIFIED):** pushes appear after `ESC i ! 00`. Implement both: send `ESC i ! 00`, and fall back to polling (§6.8).
- Large jobs: a 6-label 64 KB E560BT job printed one good label followed by blanks [teip]. **Resolution:** wait for completion after each label before sending the next.

### 6.8 Status handshake and completion (normative state machine)

1. Write one page: control block, raster lines, and `0C`/`1A`.
2. From the end of the page data until *done*, the host MUST NOT send any command, including `ESC i S`: "No command can be sent to the printer after the print data is transmitted and until the completion of printing is confirmed. Even the status information request command cannot be sent during printing" [D1 §1, D1 ESC i S note; D2–D4 alike]. The only exception is the poll fallback in step 4, which is limited to models without push status.
3. Read frames in a loop with a 10 s read timeout per read [MacSDK]. The 10 s timeout is only the loop tick: a tick that ends without data is **not** an error by itself. Process each frame in order:

   | Frame | Action |
   |---|---|
   | `st[18] = 06`, `st[19] = 01` | Printing; continue |
   | `st[18] = 06`, `st[19] = 01`, phase number `0014` | Error: cover open |
   | `st[18] = 01` | Page complete. On `start_end` models, also absorb the following phase-change frame (`06`, phase `00`) with a 2 s timeout [treideme]. |
   | `st[18] = 06`, `st[19] = 00` after printing has been seen | Done |
   | `st[18] = 02` or `18`, or `st[7]`/`st[8]`/`st[9]` ≠ 0 (any frame type, `00` included) | Error; go to §6.10 |
   | `st[18] = 05` | Notification. `03` cooling: extend the timeout (no total limit while cooling). `01` cover open: error. |
   | `st[18] = 04` | Fatal: the printer turned off |
   | `st[18] = 00` | Reply to a poll. Done if the ready predicate (§4.3) holds; otherwise keep polling. |

4. **Silence handling:**
   - Estimated print time `T_est` = 2.5 s + 10 ms per raster line (feed-direction lines actually sent; **UNVERIFIED** estimate, to be replaced by measured feed rates, §9.1). Cooling (notification `03`) suspends the clock.
   - **Push models** (status pushed during printing: P710BT/P715eBT/E720BT and P910BT/E920BT after `ESC i ! 00`; P900/P900W/P950NW with PI_RECOVER; P300BT): **never poll.** A model pushes `06`/`01` "printing" when a page starts and the completion frames when it ends, and is silent in between; a long label (up to 1000 mm, D1 §2.3.4) prints far longer than 10 s. Treat silence after a "printing" frame as normal for at least `T_est` plus a 30 s margin, and keep reading.
   - **Models without confirmed push** (E310BT/E510/E560BT, D410/D460BT/D610BT; [zakx] observed no pushes on the E560BT without `ESC i ! 00`): if no frame has arrived, wait until `T_est` has elapsed since the end of the page data, then send `1B 69 53` after every 10 s tick without data [zakx]. If a push frame is seen on such a model, switch to the push rule for the rest of the job.
5. **Overall limit:** give up after 180 read ticks without completion (≈ 30 min at 10 s per tick), as MacSDK does on Bluetooth (`checkPrintStatus`: up to 180 iterations of a read that blocks ≤ 10 s; it re-sends `ESC i S` with `sleep(1)` only on the network port) [MacSDK]. Then cancel (§6.10). A UI MAY let the user abort earlier, but a library MUST NOT cancel a print that is within `T_est` + margin. ([AndroidSDK] uses a 180 s per-read receive timeout; its 90 s value is the *send* timeout. The 90 s total used by [zakx] is a community choice for short E560BT labels and MUST NOT be used as a general limit.)
6. Only after *done* send the next page's control block (or `1B 69 61 FF` and close).

Per-model observed push behaviour:

| Model | Behaviour |
|---|---|
| P710BT | `01` completed, then `06` phase `00` |
| P300BT | 3 frames per print |
| P910BT | Pushes only after `ESC i ! 00` |
| E560BT | None observed without `ESC i ! 00` |
| P900/P900W/P950NW | Pushes when PI_RECOVER (`0x80`) is set in `ESC i z` |

### 6.9 Cutting, chaining and feeding semantics

| Goal | ESC i M | ESC i K | Notes |
|---|---|---|---|
| Cut every label, feed out the last | `40` | `08` | Default. `ESC i A n` cuts every n labels where supported. |
| Half cut between labels, full cut at end | `40` | `0C` | Half-cut models only. |
| Chain: no feed/cut after the last label | `40` or `00` | `00` | Saves the ~24.5 mm leader on the next job; the next job's first cut releases the label [D1; labelpi]. |
| No cut at all (special tape) | `00` | `10` (`18` on P710BT/P715eBT) | Fabric, stencil, etc. |
| Print cut marks (P300BT, N25BT) | `40` | `08`/`00` | No cutter |
| Feed out a chained strip | – | – | Send a 1-line blank page with `ESC i K 08` [labelpi]. Note that [labellab] observed a "precut blank page" (1 line + auto-cut) producing 3 cuts on the P710BT. |
| Trim the leading blank leader | `40` on the first page | – | [teip] (E560BT) |

### 6.10 End of job, cancel and error recovery

- **Normal end:** after the last page completes, send `1B 69 61 FF` where `sends_mode_reset_at_end` (§3.1, §6.2), then close the transport. Do not send `00×N 1B 40` immediately after `1A` without waiting: [ptouchgo] does this and it may truncate the job (UNVERIFIED).
- **Cancel:** `00×null_bytes` followed by `1B 69 18` (models in the §3.3 gate) or `1B 40` (all others) [SDK, D1–D4].
- **Error:**
  - The printer discards all received data [D2 §5.4, D4 §6.4].
  - Send the cancel sequence, wait for the ready predicate (poll `ESC i S`), report the error, and on user request resend starting with the **last page whose "Printing" phase change was received**, i.e. the page that was in progress when the error arrived. If no page reported "Printing", resend from page 1 [D1 §5.2–5.3, same flow charts in D2/D3].
  - "Printing completed" (`st[18] = 01`) does **not** mean the page has physically left the printer: Brother's flow charts show "Printing completed" and "Waiting to receive" for page 1 while page 1 is still printing. Example [D1 §5.2, p.41]: page 1 reported "Printing" and "Printing completed", page 2 never reported "Printing", then an error arrived → resend from page 1. Example [D1 §5.3, p.42]: page 2 reported "Printing" → resend from page 2.
  - Never automatically resend a partially transmitted job.

## 7. Model quirks

Machine-readable details are in [models.toml](models.toml). The key behaviours:

- **PT-P710BT** (Cube Plus):
  - Model code `0x76`. USB PID `0x20AF`. SPP on RFCOMM channel 1 (iAP2 on 2), MTU 320 [HW].
  - Insecure RFCOMM on Android.
  - No `ESC i A`, no half cut. Special tape K = `0x18`.
  - Pushes status after `ESC i ! 00`. Battery byte is always 0.
  - High-res 180×360 is supported (SDK, PTD).
  - Heat-shrink: the SDK V3 API removes HS from the list, but the V4 media list and the PTD include it. **Resolution:** allow HS 2:1 and rely on the status media check.
  - HS 3:1: not in the PTD or SDK lists; disallow.
  - [labelo] reports 80–81 printable px on 12 mm (vs 70); see §5.2.
- **PT-P715eBT:** same as the P710BT (code `0x77`, PID `0x20C5`), except that the SDK lists `HALFCUT` for it. Half cut is UNVERIFIED.
- **PT-P300BT** (Cube):
  - BT only, code `0x72`. PT3 margins: 12 mm = 32/64/32, 3.5 mm = 55/18/55. No cutter.
  - No `ESC i !`. 3 status frames after each print.
  - Drops off when idle, and reports "Host is down" on connect. Cold connect takes 3–3.7 s.
  - The official app sends 64 null bytes and margin 28. Insecure socket on Android.
  - The P300BTz variant reports code `0x80`.
- **PT-P910BT** (Cube Pro):
  - 560-pin, 360 dpi, asymmetric margins, code `0x78`, PID `0x20C7`.
  - TZe only (3.5–36 mm). No high-res or draft.
  - `ESC i ! 00` is mandatory for push status. n9 = 2 on the last page.
  - Cancel with `1B 69 18`. Battery format `2x`/`3x`. Cover-open error bit is not supported.
  - `ESC i K` bit 7 is unused.
- **PT-E560BT / E310BT / E510** (D4 generation):
  - `start_next_end`, protocol 93: send `ESC i p 01`, `ESC i L`, `ESC i C` and `1B 69 61 FF`.
  - E560BT SPP is on channel 2 (iAP on 1). Prime the multiplexer by opening channel 1 first on macOS [zakx].
  - Uncompressed by default (§5.5 conflict). Mirror in software: D4 documents the `ESC i M` mirror bit but the SDK never sets it (§3.2.2).
  - Stuck job if n9 ≠ 2: it survives a power cycle.
  - Busy ≈ 2.2 s after each label. Minimum print-data length 4.8 mm including both feed margins (34 dots) [D4]; with the default 14-dot margins that is 6 raster lines (§5.6).
  - Set Auto Power Off to Off when on AC, or the printer drops off USB [teip].
  - E310BT: max 18 mm; no half cut; no high-res; HS 3:1 up to 11.2 mm [SDK, PTD].
    - **Conflict:** D4's E310BT tables (§2.3.2(a), §2.3.5(a)) list 24 mm TZe, SL 24 mm and HS 21.0 mm with full pin tables. The SDK removes them (`PT_24mmUNSUPPORT`, `PT_HS3_24mmUNSUPPORT`) and the PTD/V4 media lists stop at 18 mm. **Resolution:** follow SDK/PTD (an 18 mm cassette bay); rely on the status media check to catch anything else.
  - E510: USB only.
- **PT-D460BT / D610BT / D410** (protocol 94):
  - Same family behaviour as the E-series.
  - D460BT/D410: max 18 mm, no high-res. D610BT: 24 mm with high-res (HR image).
  - D610BT SPP is on channel 2 [nbuchwitz#18].
  - Model codes `0x7B`/`0x7C`/`0x7A`.
  - [vowstar#24]: D610BT USB `SET_INTERFACE` timeout during init.
  - Whether these models accept PackBits is **UNKNOWN** (SDK says yes; no hardware report).
- **PT-N25BT:** BLE only, series `0x41`, model byte `0x30`, 64-pin head, raw (uncompressed) only, no battery data, no cutter (cut marks). Not usable from the macOS SDK. Entirely UNVERIFIED.
- **PT-E550W / P750W:**
  - No `ESC i !`.
  - The E550W needs compression for the cutter to fire [nbuchwitz].
  - Editor Lite PID `0x2065` (P750W) must not be used [nbuchwitz#32].
- **PT-P900 / P900W / P950NW:**
  - Status notification comes via PI_RECOVER. `ESC i !` is listed in D2's command reference without model exception, but D2's print-sequence table marks it "(PT-P910BT only)" and the SDK has no `ChangeStatusMode` for this family; the library does not send it (`supports_status_notify = false`; acceptance UNVERIFIED, §9.2).
  - Null length: D2 says 200; the SDK says 300 for P900W/P950NW. **Resolution:** use the larger value (300) where the SDK specifies it; extra NULs are harmless.
  - High-res 360×720 and draft 360×180 (`K 0x01`) are available, laminated tape only; both need `ESC i z` n1 `|= 0x02`, n2 = `0x09` [D2].
  - The P900W model code is printed as "o (69h)" in D2; it is `0x6F` [PTD, SDK, ASCII].
- **PT-D600:** [ptouch-print] reports premature cutting and a maximum length of 73 mm with its legacy sequence. [nbuchwitz PR#26] prints fine with the classic sequence, including high-res, but the SDK does not list `HIGH_RESOLUTION`. USB back-pressure blocks writes for the print duration.

## 9. Open questions and uncertainties

### 9.1 Must be verified on hardware (P710BT first)

1. **Physical orientation.** *Resolved for PT-P710BT on 24 mm* ([HW] orientation test label, PT-P710BT, 2026-10-08; §5.1, §5.3).
   - Result: pin `left` (pin 0 on 24 mm) is the top edge of upright text, so the pin mapping of §5.1 needs no flip across the tape; the first raster line received is the **right** end of the label when reading, so a left-to-right image is sent last column first (§5.3).
   - Test used: a 24 mm page with a solid bar on pins 0–7 for canvas columns 0–49, a bar on pins 120–127 for columns 50–99, a 1-dot line on pin 0, "START" and "F R 7" from column 0 and an arrow towards higher columns (`ptouch test-label orientation`), sent column 0 first. It printed with the bars and line correct across the tape and mirrored along it.
   - Still open: confirm on hardware that the fixed encoder prints the same label readable (no mirroring); repeat on 12 mm to confirm the print-area offsets (29/70/29) against [labelo]'s 80–81 px observation; check other models (only the P710BT has been tested).
2. P710BT completion frame sequence over BT with `ESC i ! 00`, and whether `1B 69 61 FF` is accepted or ignored.
3. Whether `ESC i d 0E 00` vs `00 00` changes the physical margin on P710BT. Measure the label length for a known line count.
4. P710BT high-res: whether n2 = `09` with n1 `0x02` is accepted, or `st[9] = 0x01` is returned.
5. Multi-page P710BT job with `0C` over BT: whether completion statuses arrive per page, and whether the host must wait between pages.
6. Chain printing and the "feed-out" one-line page on P710BT (labellab saw 3 cuts).
7. Minimum page: whether a page of `min_lines` (§5.6; 3 lines with 14-dot margins) prints, or whether the firmware rejects it.
8. Feed rate: time a 100 mm and a 500 mm label from the "printing" frame to "printing completed", to replace the `T_est` estimate in §6.8, and confirm the P710BT stays silent in between.
9. macOS transport in Rust: pairing (`IOBluetoothDevicePair`, incl. a PIN request), `openConnection…`/`closeConnection`, the close/run-loop drain of §2.2 step 9, and a multi-KB MTU-chunked job.
10. TCC: run the CLI from Terminal.app (no `NSBluetoothAlwaysUsageDescription`) and record whether a permission prompt appears and Bluetooth works.
11. Web Serial: Chrome on the user's Mac with the P710BT (obwat saw `open()` fail on macOS 26); also with `setSignals` on the `/dev/cu.*` node.

### 9.2 Model-specific unknowns

- E560BT family: PackBits under Brother's full sequence (with `ESC i z` 0x84, `ESC i p`, `ESC i L`/`ESC i C`). Whether `ESC i ! 00` enables pushed statuses. Brother's `0C` + n9 = 1 multi-page form.
- D460BT / D610BT / D410: no hardware report for any sequence beyond ptouch-print's experimental support. PackBits support, RFCOMM channel (D460BT), completion behaviour.
- P910BT: completion with n9 = 2. Whether `ESC i k c` is required.
- P715eBT: half cut (SDK lists `HALFCUT`; sibling P710BT has none), `ESC i A`.
- N25BT: everything (BLE framing, the sequence, status delivery).
- P300BT: `min_feed_dots` (PTD 2.4 mm = 17 dots vs SDK 14; community sends 0).
- RFCOMM channels for D460BT, E310BT, P910BT, P715eBT, E720BT, E920BT.
- Meaning of `ESC i p`, `ESC i L`, `ESC i C` beyond their documented values; `ESC i U t 1C 00`; `ESC i K 0x20` (label cut end); `ESC i k c` count semantics; the `ESC i z` n2 = `09` alternate type on 128-pin heads.
- Whether `SendDataWriteOnce` (SDK flag on D-series, E-series, P910BT and N25BT) means "send the whole job in one write". It was not traced.
- Reading status on the TCP 9100 socket (vs SNMP).
- USB PID `0x2083` collision (PT-P900 per D2 vs PT-E850TKW per SDK).
- E850TKW tube media (type `0x12`, a 144-pin tube geometry): out of scope.
- P900/P900W/P950NW: whether the firmware accepts `ESC i ! 00` (D2 command reference vs D2 sequence table "PT-P910BT only" and SDK).
- E310BT/E510/E560BT: whether hardware mirror (`ESC i M 0x80`, documented in D4) works; whether sending `ESC i k c 01 00` (SDK) changes anything.
- "Secure" models (E560BT, D610BT, P910BT, …): whether a default-security RFCOMM connection on a bonded link is accepted, or `BT_SECURITY_MEDIUM` / authenticated encryption is required (§2.1).
- `battery_format` for models marked inferred (P715eBT, E920BT, D410/D460BT/D610BT) or unknown (P300BT, P300BTz, E720BT, D450, D600, D800W, E800W, E850TKW).
- `min_length_mm` for models with no Brother doc and SDK 0 (P715eBT, P300BT, P300BTz, E720BT, E920BT, N25BT, D450, D600, D800W, E800W, E850TKW); the 4.8 mm fallback (§5.6) is a conservative assumption.
- Linux SDP: neither the BlueZ Profile API flow nor a raw SDP query (§2.3) has been run against a P-touch.
